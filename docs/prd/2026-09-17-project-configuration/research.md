## 1. Current state in this repo

### 1.1 Config loader and schema (`src/cli/config.ts`)

- `CONFIG_BASENAME = "delivery.config"`, `CONFIG_EXTENSIONS = [".json", ".js", ".mjs"]` (`src/cli/config.ts:11-12`). A `.json` file is parsed with `JSON.parse`; a `.js`/`.mjs` file is dynamically `import()`-ed and its `default` export used (`src/cli/config.ts:168-170`) — so a project can *compute* a config, e.g. read a env var, but cannot use YAML/TOML.
- `DeliveryConfig` (`src/cli/config.ts:56-64`) is a `z.object({ task, gate, closer, budgets }).strict()` — exactly the four keys the roadmap's Item 8 spec and this team's brief describe. `task`/`gate`/`closer` are `.optional()` re-exports of the library's own `TaskDef`/`GateRef`/`CloserRef` schemas (imported from `../schema.js`, `src/cli/config.ts:7`) "so the file can never drift from what the harness accepts" (`src/cli/config.ts:51-54`). `budgets` is a local partial-and-strict schema (`src/cli/config.ts:38-48`).
- `.strict()` on the top object and on `Budgets` means an unrecognised key is a named refusal, not a silent no-op (`describeProblem`, `src/cli/config.ts:82-99`), which double-checks Item 9 must *extend* this object (new optional keys) rather than leave it as-is with extra keys bolted on elsewhere — any new top-level key has to be added to `DeliveryConfig` itself or `.strict()` will reject it.
- Discovery: `configCandidates(startDir, repoPath)` walks from `startDir` up to (and including) the git repository root, testing `.json`, `.js`, `.mjs` at each level, nearest first (`src/cli/config.ts:119-129`). `loadConfig` prefers an explicit `--config`/`DELIVERY_CONFIG` path (refusing if it doesn't exist, `src/cli/config.ts:160-166`) then falls back to the first candidate that exists, then to `{}` — no config file is not an error, "because every setting has a default" (`src/cli/config.ts:143-144, 165`).
- This is a hand-rolled, single-format, single-basename version of what `cosmiconfig`/`lilconfig` do generically (§4.1) — the Item 8 spec explicitly named and rejected those libraries for this exact reason (see §2 below).

### 1.2 Settings resolution (`src/cli/settings.ts`)

- `Settings` (`src/cli/settings.ts:34-39`) is `{ taskDef, gateRef, closerRef, budgets }` — what one run needs after every source has had a say.
- Precedence, uniformly: **flag > env var > config file > built-in default**, applied independently per setting (`taskFrom` `src/cli/settings.ts:67-71`, `gateFrom` `:81-87`, `closerFrom` `:89-97`, `budgetsFrom` `:127-133`, composed in `resolveSettings` `:141-157`).
- `taskFrom`: if an explicit intent string was given (flag/file/env, resolved earlier by `explicitIntent`, `:52-65`), it becomes `{ intent }`; else the config file's `task` (a full `TaskDef`, opaque object) is used; else `NO_TASK` refuses (`:67-71`). **A run only ever has one task** — there is no task *queue* concept anywhere in this resolution path today. This is the concrete gap Item 9's "task queue" MUST closes.
- `gateFrom`: `--gate-command` builds `{ type: "command", command, parseMode: "exitcode" }` directly (flags can't select `tap`/`junit`/`custom` — those need the file); else `config.gate`; else `inferGate(repoPath)` reads `package.json`'s `scripts.test` (`src/cli/project.ts:52-56`, `:43-46`, `:58-65`), refusing with `NO_CHECK` if there's none usable (excludes the `npm init` placeholder, `src/cli/project.ts:33`).
- `closerFrom`: a bare `--closer <type>` only works for closers with no required fields (`commit-to-branch`, `merge-back`, `open-pr` — not `custom`, which needs a `modulePath`) (`:89-97`); else `config.closer`; else `DEFAULT_CLOSER = { type: "commit-to-branch" }` (`:20`).
- `ignoredSettings`/`ignoredNote` (`:105-124`): once a run exists, its `CaseFileHeader` pins `taskDef`, `gateRef`, `closerRef` for life (see §1.4); a later `delivery run` invocation's flags/env/`--config` that would have changed those are silently ignored except for one report line naming which ones, because "a run keeps the settings it started with."
- `checkCustomModules` (`:168-171`) eagerly `import()`s a `custom` gate's or closer's module *before* provisioning, so a bad module path is a CLI-level refusal, not a run-time ERROR burning budget.

### 1.3 Project inference (`src/cli/project.ts`)

- `findRepository` requires a real git repo (`git rev-parse --show-toplevel`, refuses otherwise, `:19-25`).
- `inferredCheck`/`inferGate` read the target project's own `package.json` `scripts.test`, rejecting the `npm init` placeholder string `"no test specified"` (`:33,43-46,52-56`). This is the *only* piece of "declarative discovery" that exists today, and it discovers a gate, never a task or domain prompt.
- `hasUncommittedChanges` (`:68-70`) is a `git status --porcelain` check used only to print a note (`run-command.ts:62`), not a gate.

### 1.4 `TaskDef`/`GateRef`/`CloserRef` shapes (`src/schema.ts`)

- `TaskDef = z.record(z.string(), z.unknown())` (`src/schema.ts:33-34`) — **fully opaque**. The comment explains why: "`TaskDef` is opaque to persistence (defined by a later item) and stays a passthrough JSON object." Item 9 is that later item: it is the first phase that gets to say what shape a `TaskDef` actually has (beyond the one convention every caller already uses, `{ intent: string }` — `src/cli/settings.ts:42-44,68`, `src/cli/init.ts:135`).
- `GateRef` (`:36-50`) is a `z.discriminatedUnion("type", [command, custom])`. `command` needs `command` + `parseMode: "tap"|"junit"|"exitcode"` + optional `failOnNewAssertions`. `custom` needs `modulePath` + optional `exportName`/`failOnNewAssertions`. No named presets (e.g. "eslint", "vitest") exist; every project writes its own shell command.
- `CloserRef` (`:60-78`) is a `discriminatedUnion` over `merge-back` (+ optional `deleteBranch`), `commit-to-branch` (no params), `open-pr` (no params), `custom` (+ `modulePath`/`exportName`). `BUILT_IN_CLOSERS` in `config.ts:18-20` derives the closer-type list straight from this union "from the library's own list so the two can never disagree" — the pattern Item 9's gate/closer name-selection UI should reuse rather than re-list.
- `CaseFileHeader` (`:129-144`) pins `surfaceId`, `taskDef`, `gateRef`, `closerRef` (optional, back-compat), **`domainPrompt?: string`**, `baseline`, `baseBranch` at `CREATE` time — immutable for the surface's life. `domainPrompt` is fully plumbed through persistence and prompt assembly (see §1.6) but **`src/cli/run-command.ts:68`'s call to `create(dir, { surfaceId, taskDef, gateRef, closerRef }, budgets)` never passes it** — grep confirms `domainPrompt` is set only in tests and design-doc examples, never by any CLI code path (`src/case-file.test.ts:31,621`, `src/prompt-assembly.test.ts:32`, no hits in `src/cli/*.ts`). **This is the concrete gap for the "domain system-prompt fragment" MUST**: the schema and the prompt-assembly consumer exist; only a producer is missing.

### 1.5 Role configs and prompt assembly

- `RoleConfig<E>` (`src/role-config.ts:39-52`) is a plain TypeScript interface: `{ role, systemPromptFragment, envelopeSchema, allowedTools, budgets? }`. `workerRoleConfig` and `gateMaintenanceRoleConfig` (`:65-99`) are **exported `const` literals in source** — a project extends the harness today by writing its own TypeScript module that builds a `RoleConfig` object, not by editing a config file.
- `validateRoleConfig` (`:127-134`) parses a `RoleConfig` against `RoleConfigShape`, a zod schema built for validation only — the runtime type itself is not a zod schema (`envelopeSchema` is checked with `z.custom(...instanceof z.ZodType)`, `:105-107`), and a `triage` role's `allowedTools` is refined to only `READ_ONLY_TOOLS = ["Read","Glob","Grep"]` (`:59, 111-120`). This validation exists and is cheap to reuse for any declarative role-config surface Item 9 adds.
- `src/cli/drive.ts:37-40` wires role configs into a run: `createAgentPort({ worker: workerRoleConfig, "gate-maintenance": gateMaintenanceRoleConfig, triage: triageRoleConfig }, session)` — a hardcoded, static import. **There is no seam today for a project's config file to override or replace a role's `systemPromptFragment` or `allowedTools`** — confirmed explicitly by the Item 8 spec: "Item 8 adds no role-config or system-prompt field; overriding a role's `systemPromptFragment` or `allowedTools` stays a library-level code choice until Item 9 designs its authoring surface." (`docs/superpowers/specs/2026-09-14-cli-and-configuration-design.md:180-185`).
- `triage-role-config.ts` (69 lines) similarly hardcodes `triageRoleConfig` and defines `SharpenedBrief` (the triage artefact shape prompt-assembly reads, `src/prompt-assembly.ts:5,37`).
- `assemblePrompt(caseFile, roleCfg, evidence)` (`src/prompt-assembly.ts:98-156`) is a **pure function**: same case file + role config + evidence → byte-identical prompt (stated goal at `:94-96`). System prompt = `roleCfg.systemPromptFragment` + `\n\n` + `caseFile.header.domainPrompt` if present (`:103-107`); user prompt is five fixed sections — Task (raw `JSON.stringify(taskDef)`), Brief, Gate evidence, (Setback, triage only), Reply format (`:139-153`) — in an order the project cannot reorder or drop, "if a project could reorder or drop a slot it could tell a worker not to emit an envelope" (`:86-92`). **Any prompt-preview command Item 9 builds can call this exact function** with a synthetic/dry-run case file and the resolved role configs — no new rendering logic is needed, only a way to construct the inputs without provisioning a surface.
- The envelope schema itself is rendered into the prompt as JSON Schema via `z.toJSONSchema(roleCfg.envelopeSchema)` (`:130`) — confirming **zod 4's built-in `z.toJSONSchema()`** is already used in this codebase for schema-to-JSON-Schema conversion, which matters for §4.2 (no separate `zod-to-json-schema` dependency needed).

### 1.6 Tool authority (`src/tool-authority.ts`)

- `createToolAuthority(roleCfg, worktreePath)` builds the SDK's `canUseTool` callback from exactly two facts on `roleCfg`: the positive `allowedTools` list, and the worktree boundary (`:88-105`). Refusal sentences (`refusalSentence`, `outsideWorktreeSentence`, `:16-39`) are written to be read by a non-technical human. **`allowedTools` is the entire blast-radius surface a declarative config would need to expose** — there is no separate "domain tools" concept beyond this list; the roadmap's Item 9 text ("domain system-prompt fragment (role identity, domain context, domain tools)") maps directly onto `systemPromptFragment` (identity + domain context, free text) and `allowedTools` (domain tools, an array of SDK tool names).

### 1.7 How `delivery run` composes a run

- `runCommand` (`src/cli/run-command.ts:26-45`): finds the repo, checks for an unfinished run (unless `--fresh`), resolves the intent the user typed just now; if an unfinished run exists it either resumes the one the user's intent matches or, with no intent given, asks interactively (`chooseRun`, `src/cli/runs.ts`) — else starts fresh.
- `startRun` (`:48-75`): loads config, resolves settings (§1.2), eagerly checks custom modules, gets the agent session, notes uncommitted changes, derives a run id from the intent + timestamp (`runIdFor`), prepares the run directory, **creates the case file** (`create(dir, { surfaceId, taskDef, gateRef, closerRef }, budgets)` — note: no `domainPrompt`, confirming §1.4), then hands off to `driveToOutcome`.
- `driveToOutcome` (`src/cli/drive.ts:29-56`): builds the static `agent` port from the three hardcoded role configs (§1.5), the deterministic router as `triage`, and `resolveCloser(header.closerRef ?? DEFAULT_CLOSER, repoPath)` as `closer`; then loops `advance(dir, location, ports)` until `done`, printing one line per state transition, and finally summarises the outcome.
- `resumeRun` (`:64-71`) re-checks custom modules (in case a module moved since the run started) and re-enters `driveToOutcome` with the *persisted* header's settings — never re-resolving flags/env/config.
- `src/cli/runs.ts` (164 lines) implements `unfinishedRuns`, `chooseRun` (interactive picker over `@inquirer/prompts`, when several are unfinished and no intent disambiguates), and the CLI-facing `RunRecord` shape (`caseFile` + `runId` + `repoPath` + `dir`). There is **one run = one task** throughout; nothing here iterates a queue.

## 3. Comparable tools — declarative config, validate, preview/dry-run, task queues

### 3.1 Config discovery conventions

`cosmiconfig` is the de facto standard config-discovery library — used by ESLint, Prettier, Babel, PostCSS, etc. — searching a fixed set of filenames/extensions up the directory tree with an in-memory cache; `lilconfig` is a zero-dependency, ~30%-smaller drop-in with the same API but no YAML support by default (npm/GitHub listings, search results above). Both are irrelevant here per the Item 8 spec's own reasoning (§2): this repo's single-basename, three-extension, JSON-or-computed-JS walk-to-repo-root (`configCandidates`, `src/cli/config.ts:119-129`) already *is* a hand-rolled cosmiconfig-shape loader, deliberately kept minimal because YAML is a non-goal.

### 3.2 Validation / dry-run commands with no side effects

- **Terraform**: `terraform validate` is a fully local, offline syntax/internal-consistency check — no provider APIs, no state, no credentials needed, fastest signal ("catch typos, missing arguments, type mismatches... before you reach plan or apply", search result above; Spacelift/Firefly/DevToDevOps summaries agree). `terraform plan` is a heavier dry-run that *does* call provider read APIs to compute a diff, but still performs no mutation. This maps to two possible tiers for `delivery validate`: a pure schema/completeness check (no repo/network access, Terraform-`validate`-equivalent) versus a "what would actually happen" preview that may need to read the target repo (`package.json`, git state) — closer to Terraform `plan`. This repo's existing `inferredCheck`/`findRepository` (§1.3) already do lightweight repo reads without side effects, so a `plan`-style richer preview is cheap to build on, not a new capability class.
- **GitHub Actions / actionlint**: `actionlint` is a static, local checker for workflow YAML — syntax, `${{ }}` expression type-checking, action `with:`/`outputs:` validation, `needs:` dependency graph checks, cron syntax, script-injection detection (rhysd/actionlint docs, search above). Notable pattern: it validates *cross-references* within the file (a `needs:` graph, action input/output contracts), which is the same class of check `delivery validate` needs for e.g. a task queue referencing a gate preset by name, or a closer referencing a role that doesn't exist.
- **ESLint/Prettier `--print-config` / config validation**: both tools validate their own config schema on every invocation and refuse with a specific message naming the bad key — the same shape as `describeProblem` in this repo (`src/cli/config.ts:82-99`), already built.

### 3.3 Declarative task queues / runners

- **Taskfile (go-task)**: a single `Taskfile.yml` per project declares named tasks with `cmds`, `deps`, `vars`, `env`, and an `includes` mechanism to compose Taskfiles (search result above; `taskfile.dev/docs/guide`). It is a *runner*, not a work queue with state — closer to this repo's `GateRef`/`CloserRef` "name + params" shape than to a task queue with pending/in-flight/done states. Relevant precedent for Item 9's task-queue key: tasks as a flat, named/ordered list in the config file itself, no external queue engine.
- **Make**: implicit precedent, not separately searched — same "named targets, declarative dependencies" shape; not a natural-language source.

### 3.4 AI-agent tools: declarative project/task config

- **Aider**: `.aider.conf.yml` (repo root or home directory) is the project-level config — model selection, linting (`lint: true` + `lint-cmd:`, output fed back to the model for self-correction), auto-commit, and a `read:` key naming files (e.g. `CONVENTIONS.md`) to always load as context (aider.chat docs, search above). This is the closest existing-tool analogue to this repo's `domainPrompt`: a small set of *prose files* loaded verbatim into every session's context, rather than a schema the tool parses. Directly relevant to the "domain context authored in prose" MUST: Aider's answer is "point at a markdown file, load it verbatim" — no NL→structured-data step at all for context, only for the optional per-invocation instruction (typed directly, not templated).
- **Cursor rules**: `.cursor/rules/*.mdc` — Markdown with YAML frontmatter (`description`, `globs`, `alwaysApply`) controlling *when* a rule fragment is injected into context, replacing the older single always-loaded `.cursorrules` file (search results above). Pattern worth weighing for the "domain system-prompt fragment": frontmatter-plus-markdown is a natural authoring format for prose context a human writes directly (no NL→structure step), and file-glob-scoped activation is a possible future refinement — but out of scope for a MUST tier that only needs one domain prompt string per project.
- **Claude Code itself (this tool)**: `CLAUDE.md` (project) and `~/.claude/CLAUDE.md` (user) are plain prose markdown files loaded into context automatically — no frontmatter, no schema, human-authored free text. `settings.json`/`settings.local.json` hold the *structured* configuration (permissions, hooks, env vars) as JSON with its own schema. This is the same two-tier split this repo already has in embryo: `domainPrompt` (prose, unstructured) and `delivery.config.json` (JSON, `.strict()`-schema'd) — evidence this split is a proven, working pattern for exactly this kind of tool, not a novel design.
- **OpenHands, Sweep, Devin**: not independently re-verified in this pass (training-era knowledge, not web-confirmed this session) — flagged so the team does not cite these without a fresh check if a specific claim about them becomes load-bearing.

## 4. Candidate libraries — trade-offs

Checked against `package.json` (`dependencies`: `@anthropic-ai/claude-agent-sdk`, `@inquirer/prompts`, `commander`, `zod@^4.5.4`; `devDependencies`: `@changesets/cli`, `eslint`, `@jorj/claude-mock` (vendored), `tsx`, `typescript`, `vitest`, plus typescript-eslint/types). **No cosmiconfig/lilconfig, no gray-matter, no YAML/TOML parser, no zod-to-json-schema is installed today.**

| Capability | Candidate | Trade-off |
|---|---|---|
| Config discovery | `cosmiconfig`/`lilconfig` vs. extend `src/cli/config.ts`'s existing walker | The existing walker is ~15 lines, already tested, and the Item 8 spec explicitly reserved a discovery library for "only if Item 9 needs YAML" (`cli-and-configuration-design.md:562`). Brief's non-goals rule out YAML/TOML. **Extend the existing loader**; pulling in a library here would be solving an already-solved, deliberately-scoped-down problem and add a dependency for zero new capability. |
| JSON Schema for editor validation | `zod-to-json-schema` (external) vs. `z.toJSONSchema()` (zod 4 built-in) | `z.toJSONSchema` is **already used** in this codebase (`src/prompt-assembly.ts:130`, to render the envelope schema into a worker prompt). Zod 4.5.4 is already the installed version. No external dependency needed for any "emit a JSON Schema for `delivery.config.json` so an editor can validate it" capability — call `z.toJSONSchema(DeliveryConfig)` (or an Item-9-extended equivalent) directly. |
| Human-readable zod error formatting | `zod-validation-error` (external) vs. `describeProblem` (existing, `src/cli/config.ts:82-99`) vs. zod 4's own `z.prettifyError()`/`z.flattenError()` | This repo already hand-rolls plain-language, first-issue-only error prose tuned to this project's exact vocabulary (naming `CONFIG_KEYS`, quoting the bad value, special-casing `closer.type` and `budgets.*`, `src/cli/config.ts:82-99`). `zod-validation-error` produces generic, config-agnostic prose; adopting it would be a regression from the existing tailored messages, not an improvement — and zod 4's own `prettifyError`/`flattenError` are even more generic. **Extend `describeProblem`** with new branches for whatever keys Item 9 adds, following the existing pattern; do not add a library here. |
| Markdown/front-matter parsing for task files | `gray-matter` (external, YAML/JSON/TOML front matter, used by Gatsby/Astro/VitePress/many others) vs. no parsing (prose-only files, Aider's model) | Only relevant *if* the design decides task/domain files are separate `.md` files with metadata headers rather than JSON fields in `delivery.config.json` or plain strings. Given the brief's non-goal on YAML/TOML and the existing `domainPrompt: z.string()` shape, the lower-cost path is a **plain string field** (typed directly in the config file, or read verbatim from a referenced `.md` file with no front-matter parsing at all — Aider's `read:` pattern, §3.4). If the product design nonetheless wants per-task metadata (e.g. priority, role hints) alongside prose, `gray-matter` is the right, well-precedented tool for that — but it is a decision for the product designer to make explicitly, not a default. |
| Config validation | Existing `zod` schemas, composed | No alternative considered; already the mandated pattern (`docs/superpowers/specs/2026-09-14-cli-and-configuration-design.md:565`: "Reuse `zod`... Composes the library's existing `TaskDef`, `GateRef`, `CloserRef` schemas, so the CLI adds no parallel contract"). Item 9 must keep composing, not restate. |

## 5. Natural-language task → structured `TaskDef`: options

`TaskDef` is `z.record(z.string(), z.unknown())` (`src/schema.ts:33`) — genuinely opaque; the harness never branches on its shape, only serialises it into the prompt verbatim (`JSON.stringify(caseFile.header.taskDef, null, 2)`, `src/prompt-assembly.ts:141`) and reads `.intent` by convention for logging/run-naming (`taskIntent`, `src/cli/settings.ts:42-44`). Two genuinely different design directions:

### 5.1 Deterministic: prose passed through, or thin markdown convention

- Simplest possible producer: a task queue entry is `{ intent: "<prose the owner typed>" }`, exactly what `--task` already builds today (`src/cli/settings.ts:64,68`) — the "natural-language task" *is* the `TaskDef`, with `intent` the one field every consumer already reads. No structuring step at all.
- A markdown-file convention (one task per file or a list under headings) needs only a splitter, not front-matter parsing, if the only structure is "task boundary" + "free prose body" — regex/line-based, zero dependencies.
- **Costs**: none beyond writing the splitter; fully deterministic (same file → same queue, byte for byte); trivially testable with plain input/output fixtures — matches this codebase's stated value ("Determinism is testable: same case file → byte-identical prompt", `docs/superpowers/specs/2026-09-09-agent-invocation-primitive-design.md:108-109`, a bar Item 9's producer should meet too).
- **Costs of *not* structuring further**: a worker gets only prose, with none of the role-targeted "what each role needs" the roadmap asks for (Item 9 success criterion: "Task definitions can be authored with the context each agent role needs, and validated before dispatch," `delivery-harness-roadmap.md:370-371`). If different roles genuinely need different views of the same task, a flat prose string doesn't distinguish them — but nothing in the current `RoleConfig`/prompt-assembly seam reads anything from `taskDef` beyond the single JSON blob shown to every role identically (`src/prompt-assembly.ts:139-141` — task section is the same for worker, gate-maintenance and triage), so "context each role needs" may currently be satisfiable by the domain prompt + task prose alone, without per-role task fields. This is a product-design judgement call, not a research finding, but the current architecture does not force per-role task structuring — it forces per-role *system prompt* differences only.

### 5.2 Agent-assisted structuring

- An LLM call (or a call to the harness itself, per the roadmap's COULD-tier "agent-driven onboarding," `delivery-harness-roadmap.md:432-437`) turns free prose into a richer `TaskDef` (e.g. explicit scope/acceptance-criteria fields) before it is queued.
- **Costs**: non-deterministic by construction — the same prose could structure differently between runs unless the call is cached/pinned, breaking the "same case file → byte-identical prompt" guarantee this codebase currently holds as a design invariant for the *prompt*, though note that invariant is about `assemblePrompt`, not about how `taskDef` was produced; once a `TaskDef` is persisted in the case file header it is immutable regardless of how it was authored (`CaseFileHeader.taskDef`, pinned at `CREATE`, `src/schema.ts:129-143`). So the determinism risk is confined to *authoring time* (does re-running `delivery validate` on the same queue file produce the same structured tasks?), not to run-time prompt assembly.
- Needs an agent call before any gated work starts — real cost (API spend, latency, an extra failure mode) for what the brief's success criterion 3 says must be free: "`delivery validate`: completeness and consistency check before a run, no agent spend." If structuring happens inside `validate`, that directly contradicts this requirement; if structuring happens at a separate, explicit "propose a config" step (the roadmap's COULD tier), it's consistent — but that keeps agent-assisted structuring out of the MUST-tier `validate` command by construction.
- Testing implication: agent-assisted structuring cannot be tested with the existing `claude-mock` scripted-double pattern (`src/mock-script.ts` per the guide-as-test convention, §1.9) without either scripting the mock's structuring reply too (extra fixture per test) or accepting non-determinism in test fixtures — a real testing cost, not just a design one.

### 5.3 Implication for the MUST tier

Given `delivery validate` must cost no agent spend (brief, Item 9 success criterion), and the brief's MUST #2 says tasks are "structured into what each role needs... validated before dispatch," the deterministic path (§5.1) is the only one that can satisfy *both* constraints inside the MUST tier. Agent-assisted structuring (§5.2) fits cleanly only as the explicitly-named COULD tier ("agent-driven onboarding that proposes a configuration for owner approval") — which matches the roadmap's own COULD-tier framing (`delivery-harness-roadmap.md:432-437`, phrased as "the spec should also consider," not a success criterion). This is a strong signal for the product/architecture drafts, not yet a decision — flag for the critic.

## 6. Open questions for the designers (not resolved by research)

1. Where does a task queue live — one array in `delivery.config.json`, or separate files it references? (§3.3, §5.1)
2. Is `domainPrompt` authored inline as a string in the config file, or read from a referenced file (Aider's `read:` pattern, §3.4)? Either is a one-line change to `startRun`'s missing `create(...)` argument (§1.4) — the gap is the same either way.
3. Does role-config override (`systemPromptFragment`/`allowedTools`) belong in `delivery.config.json` directly, in a separate file it references, or both? `RoleConfigShape`/`validateRoleConfig` (`src/role-config.ts:101-134`) already validate the target shape and can be reused regardless.
4. Named gate/closer presets (roadmap's Item 2 Accessibility note, §2): a preset is sugar over `GateRef`/`CloserRef` — does it live as data (a lookup table) or code (functions returning a `GateRef`)? Either composes with the existing `discriminatedUnion` without schema changes.
