## Critic log


### Critic: verdict on phase selection and MUST/SHOULD/COULD split (round 1)

- **Phase: PASS.** Item 12 is next in roadmap order, all dependencies shipped, Items 8-11 specs defer packs to it (multi-surface design lines 44, 593), no duplication with shipped specs (no spec defines a pack, finding schema or scan phase). Not a pivot.
- **Scoping: FAIL (value-starvation).** The roadmap's Item 12 success criteria name two packs as deliverables: code review AND security review (own criteria for severity categorisation, owner-legible risk, vulnerability-closed gate). Demoting the security pack, severity and authority-class escalation to SHOULD means a MUST-only release fails half the roadmap's stated success criteria, and leaves Item 13's headline use case ("security review every Sunday") without its pack. A single shipped pack also cannot show that the pack format generalises. The per-finding gate ("verifies the specific issue is resolved") is a roadmap success criterion for both packs, so it is MUST, not SHOULD. Dana's primary journey needs both packs.
- **Required revision:** MUST = pack format; scan->owner review->fix flow; code review pack and security review pack, both with per-finding targeted gate; plain-language findings; unresolvable findings escalated. Security severity threshold and authority-class default may stay a MUST on the security pack (roadmap-specified default) with the threshold's configurability as SHOULD. COULD = third-party pack discovery/distribution. The gate-weakening idea may be named as a risk the per-finding gate must withstand.
