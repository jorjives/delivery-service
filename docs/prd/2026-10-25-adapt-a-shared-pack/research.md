## 1. Verified facts about the current code

### 1.1 Pack manifest `/3`

- Versions read: `["delivery.pack/2", "delivery.pack/3"]` (`src/packs/pack-format.ts:8`); version written `delivery.pack/3` (`:12`).
- `PackManifest` is a `z.strictObject` with `$schema?`, `schema`, `name`, `version`, `title`, `summary`, `workflows` and nothing else (`pack-format.ts:69-78`). Unknown keys are refused.
- Workflow = discriminated union on `kind`: find `{prompt, ideasFor}` (`:44-48`), act `{prompt, summary?, guards?: {add: GuardName[]}, hold?: {atOrAbove: Severity}}` (`:50-56`). Strict objects throughout.
- `hold` is already an object, `{ atOrAbove }` (`:55`); `/2` held a scalar `hold: Severity` (`:40`), absorbed by `upgradeV2` (`:100`).
- `settings` is reserved only by a sentence: `"settings" is reserved for pack settings, which this harness does not read yet` (`src/packs/pack-rules.ts:68`). That sentence fires from the unrecognised-key path, so it is not a schema key.
- `{{settings.` is documented as reserved (`docs/writing-a-pack.md:128`) but **nothing enforces it**: grep of `src/`, `packs/` and `docs/` finds no loader code reading it, only the prose and specs. A `/3` prompt containing `{{settings.x}}` today loads and is sent to the agent as written. Consequence: any existing `/3` pack in the wild that happens to contain such text would change meaning when substitution arrives (very low probability; no built-in uses it, architecture.md:169 of the packs-for-any-workflow bundle says "no existing prompt uses it").
- Data-only sentence: `DATA_ONLY` = "is not part of the pack format: a pack holds only data, so it cannot give the agent tools or commands, or bring code of its own for its check" (`src/packs/manifest.ts:114-115`).
- Published schema: `packSchema()` = `z.toJSONSchema(PackManifest, {io:"input"})` (`pack-format.ts:86`). Stability test is per version lines in `src/packs/pack-published-keys.txt` (26 `/2` lines, then `/3` lines at 28-58). Both directions are tested: every promised line must remain, and every current line must be in the file (`pack-format.test.ts`; same pattern for inspection at `src/packs/inspection-schema.test.ts:34-38`). Optional keys are recorded as `(optional)` (`src/report/json-schema.ts:56`).
- `Sentence` (single line, no hidden characters, `pack-format.ts:15-19`) and `hasHidden` (`src/packs/hidden-characters.ts:7-13`, Unicode Cc/Cf/Zl/Zp) are existing precedents for constraining author text.

### 1.2 Loader, hash and approval

- `readPack(dir)` (`manifest.ts:270-322`) and `loadPack(dir)` (`:326`) take **only a folder**. They have no project, no config, no values. Callers: `builtInPacks` (`:334`), `projectPackStates` listed folders (`src/cli/pack-workflows.ts:14`), `checkInstalledPack` via `readPackFolder` (`src/packs/install/installed.ts:49`), and the `packs inspect/approve/update` commands (`src/cli/packs-inspect-command.ts:56`, `packs-approve-command.ts:56`, `packs-update-command.ts:117`). Any design that substitutes values in the loader must either change that signature or bind values in a later step.
- `packWorkflows` (`manifest.ts:201-231`) builds each pack workflow into a `WorkflowConfig`: one step, `prompt = promptOf({authored, harness})`; a find gets `guards:{add:["backlog-only"]}` and `after: []` (`:221`); an act gets its manifest `guards` and `hold: workflow.hold.atOrAbove` (`:227`). **No step carries a `gate`**: a pack step is judged by the project's gate.
- The fingerprint (`Pack.hash`) is sha256 of the raw `pack.json` bytes then each prompt's text in sorted workflow-name order for `/3` (`manifest.ts:235-239, 319-321`). The lock stores `fingerprint` and `approved` as `delivery.pack-hash/1:<hex>` plus a digest per covered file (`src/packs/install/lock.ts:12-34`); covered files are `pack.json` and each named prompt (`digests.ts:7`).
- Per-use state check (`installed.ts:46-65`): missing, invalid, changed (fingerprint differs), unapproved (`approved !== fingerprint`), else ok. `refuseUnusable` refuses before any agent call (`:88-91`).
- Facts for R§3: owner values, if kept in `delivery.config.json`, are **not in any fingerprinted file**. A pack that adds or changes a `settings` declaration changes `pack.json` bytes, hence the fingerprint, hence "changed" until the owner re-approves through `update`/`approve`.
- Built-in packs are in `packs/` (`code-review`, `deprecations`, `security-review`); `code-review` and `security-review` are `/2` (`packs/code-review/pack.json`), `deprecations` is `/3` with `hold.atOrAbove: "high"` on its `code` act. Built-ins are not fingerprinted by the install lock (they ship with the harness).

### 1.3 Where project configuration names packs

- `delivery.config.json` is `.strict()` (`src/cli/config.ts:220`); `CONFIG_KEYS` lists the allowed top-level keys: `task, tasks, domain, agent, gate, closer, budgets, concurrency, fence, workflows, packs, sources, after, parkAfter, notify` (`config.ts:22`).
- `packs` is `z.array(Written)` of **folder paths** (`config.ts:210`; sentence at `:295`). It has no per-pack object, so there is no existing place to attach values to a pack by name.
- Built-in packs and **added (installed) packs are never named in the config**. `projectPackStates` loads all built-ins, then each listed folder, then every `ok` installed pack read from `.delivery/packs.lock.json` (`pack-workflows.ts:12-18`). Values for an installed or built-in pack therefore need a key keyed by pack name, not an extension of `packs`. (FACT about current shape; the choice of key is the architect's.)
- Terminology collision: in code, "settings" already means the **whole parsed project configuration** (`loadConfigAndPacks` returns `{config, settings, packs}`, `config.ts:554`; `src/cli/settings.ts` is the project-resolution module with `ProjectSettings`). User-facing prose says "project configuration". A pack "setting" is a new meaning; naming needs care (ambiguity A7).
- The config can be `.js` as well as `.json` (`config.ts:520-525`, `checkConfig` imports it). `findConfig` with `dataOnly` ignores non-JSON (`config.ts:513`). Inspection reads config "from data only" and reports `config: "code"` for a `.js` file without reading it (`src/cli/project-baseline.ts:43-44`; `ProjectBaseline.config` enum at `inspection.ts:23`). So **owner values held in a `.js` config cannot be shown by inspection** as it works today.
- No JSON Schema exists for the project configuration (the only `toJSONSchema` uses are the agent envelope `prompt-assembly.ts:217`/`agent-invoke.ts:234`, `report/json-schema.ts:17`, and `packSchema` `pack-format.ts:86`). This confirms the roadmap's Item 6 note.

### 1.4 Prompt interpolation

- `TASK_PLACEHOLDER = /\{\{task\.([A-Za-z0-9_]+)\}\}/g` (`src/prompt-assembly.ts:100`). `interpolateTask(prompt, taskDef)` replaces with `fieldText` (string/number/boolean as written, anything else compact JSON, `:104-110`), leaving an unmatched placeholder as written. It is applied to **one place only**: the `## Step` slot (`:234`). Not to the system prompt, `domain`, `agent.append`, or the `## Task` block.
- `String.replace` with a callback does not rescan its output, so a value that itself contains `{{task.x}}` is not re-expanded (JavaScript semantics, not a repo claim).
- `unmatchedPlaceholders` is used only by `delivery preview` to warn `Warning: step ... has the placeholder ..., and the task has no such field, so the agent would be sent it as written.` (`src/cli/preview-command.ts:36-37, 172`). A run does not warn or refuse on an unmatched placeholder.
- `assemblePrompt` is documented pure: "The same case file yields a byte-identical request, so a reconstructed session after a crash is the same session" (`prompt-assembly.ts:189-191`, in the doc comment above `assemblePrompt`). Anything substituted at assembly time must therefore come from the case file.
- Workflows are **pinned** into the case file at create: `PinnedWorkflow {name, steps: WorkflowStep[], hold?}` with `step.prompt` as text (`src/schema.ts:215-228`; built by `workflowFrom`, `src/cli/settings.ts:133-138`). `taskDef` is a separate header field (`schema.ts:~293`). So resolving settings **before pinning** (at `workflowFrom`) gives a run whose recorded prompts and hold already hold the values; resolving at assembly needs a new header field.
- Task fields: a backlog item's every front-matter field is a task field (`src/backlog.ts:109-112`, `itemTask`); a GitHub issue's labels/body likewise (`src/github-source.ts:78`); a `command` source's JSON fields likewise (`src/work-sources.ts:64-65`). Items from a tracker are flagged `untrusted` (`sources-run.ts:287-291`) and the task block gets `UNTRUSTED_TASK` (`prompt-assembly.ts:275`) **before the task JSON, not before the Step slot**. INFERENCE (from reading `assemblePrompt` `:~235-262`): a `{{task.body}}` in a step prompt puts tracker-written text into the Step section with no untrusted notice beside it.

### 1.5 What command gates can see

- `GateRef` command variant: `command, parseMode, failOnNewAssertions?, checkOnly?, setup?, teardown?` as plain strings (`src/schema.ts:66-79`).
- `GateContext` carries `taskDef` (`command-gate.ts:7-10`; filled at `run-gate.ts:21-23`) but `createCommandGate(command, ...)` is built from `ref.command` at resolve time (`resolve-gate.ts:25-26`) and passes only `cwd`, `env` to `runShell` (`command-gate.ts:100-110`). The only per-run value in the env is `DELIVERY_STEP_START` (`run-gate.ts:14-16`). Confirmed: **command gates cannot see task fields** at HEAD, matching the packs-for-any-workflow research (`docs/prd/2026-10-23-packs-for-any-workflow/research.md:111`).
- `runShell` runs `/bin/sh -c`, and offers `args` as positional parameters `"$@"` "so a value the harness passes (an item id) is never read as shell text" (`src/shell.ts:10-13`). Existing in-estate precedent for passing a value to a shell command without it being shell text.
- Custom (code) gates do get `taskDef` (`GateContext`, `custom-gate.ts`); that is why the survey's examples used them. The survey: "A command gate cannot see the task's fields. The migration and upgrade examples need a custom gate module only to read `file`, `package` and `to`. Passing the task to a command gate (an environment variable naming a JSON file, say) would let them be one-line commands." (`git show 52e236b:docs/research/2026-10-20-ai-workflows.md`, "Defects and gaps", item 5; the file is on another branch, not in this worktree.) Note the fields named are **per-task** (`file`, `package`, `to`), not per-project.

### 1.6 Guards, checks and hold built from a pack

- Guards: an act's `guards.add` becomes the step's `guards` switch (`manifest.ts:226`), joined to the defaults by `activeGuards` (`src/task-guards.ts`). The names are a closed enum (`schema.ts:36`).
- Item "checks" (`anchor-gone`, `pattern-absent`, `dependency-absent`) are closed, harness-owned and written **by the scan agent into each idea** (`schema.ts:~48-60`, `ideaFormat` `manifest.ts:~24-57`). A pack does not declare a check; it only supplies the scan prompt. So "values reach the pack's ... checks" has no direct referent in `/3` (ambiguity A3).
- Hold: `heldFor` reads `caseFile.header.workflow?.hold` (`src/surface.ts:782-788`), the pinned workflow's value. A settable hold severity would therefore be resolved before pinning.
- The gate that judges a pack's work is the project's: the acceptance text says "the project's check" unless the step has its own `gateRef` (`prompt-assembly.ts:~64`, `gateLines`), and a pack step has none (R§1.2). The project's own gate is already configurable (`gate`, `config.ts`; inferred as `npm test` from `package.json`, `src/cli/project.ts:85-98`). A pack "test command" setting would duplicate that, unless it is meant only for prompt text (A2).

### 1.7 How inspection renders a pack

- `Inspection` (zod, `src/packs/inspection.ts:54-76`): `pack{name,version,title,summary,format,hash,source,workflows}`, `defaultGuards`, `workflows[]` (each: name, local, kind, summary, offers, steps[{name, instructions{authored,harness}, guards}], upgraded, widens, hold), `project: ProjectBaseline`, `files`, `widens`, `findings`, `hiddenCharacters`. Instructions are the **raw** pack text, placeholders unresolved (`inspection.ts:94-96`).
- `ProjectBaseline` already makes inspection project-aware: it reads the project's gate and closer from the config, from data only, and degrades to `none/code/unreadable` (`project-baseline.ts:24-60`). A "values that would apply" section would follow the same route (find the config, read, match by pack name). `inspect` can be pointed at a folder that is not in the project (`packs-inspect-command.ts`), so "would apply" must say what it does for a pack the project does not name.
- Stability: every inspection key is under the published-keys promise (`inspection-schema.test.ts:34-38`) and **no key may be optional** (`:32`). The architecture note's "optional `settings` array" (inspect `architecture.md:156`) must therefore be read as "an always-present array, empty when the pack declares none"; a truly optional key would fail the existing test. New keys are additive and need their lines added to `src/packs/pack-inspection-published-keys.txt`.
- `comparePacks` (update report) builds a `Change` union from two inspections: hold, guard, workflow, kind, widens, finding kinds, each with a direction (`src/packs/install/compare.ts:6-18, 20-37`). A changed default, a new required setting or a removed setting is not a kind today; the update report would not mention it unless `Change` grows (the schema comment says "The update document publishes these").
- Hidden characters are scanned over inspection text (`inspection-findings.ts`, `hiddenCharactersOf`); values would need the same.

### 1.8 Other facts

- `packs check` runs a pack's fixtures against the scripted agent (`src/cli/pack-check.ts:107`); `fixtures/project/` has no project config, so a pack with a required setting needs a way to receive fixture values or defaults in `packs check` (new: not designed yet).
- `delivery preview` renders the exact prompt a step would send (`preview-command.ts:170-180`), the natural place to show resolved values (not named in the roadmap).

### Patterns the prior art supports

1. **Declare, default, validate, refuse by name.** Helm's schema and Terraform's `type`/`validation` show the declaration carrying its own validation. Delivery's closest in-estate machinery is zod plus `Sentence` and the pack-problem sentences (R§1.1).
2. **Required is a property of absence of a default** (Terraform) or an explicit flag (Actions, Helm schema). Actions shows the failure mode of leaving enforcement to the author: it is the harness that must refuse, matching the roadmap's "refused with a message naming it".
3. **Everything-is-a-string (Actions) versus typed values (Helm schema, Terraform).** Prompts consume text, so a text rendering is needed regardless; typing matters for `hold` (enum of `Severity`) and for list values (file layout).
4. **Injection arises when a value is expanded into an interpreter.** Actions and cookiecutter hooks are the cautionary cases; the mitigation is not to put the value in script text (env variable in Actions; positional parameters, which `runShell` already offers). For a prompt, "injection" means values that change what the agent is told: hidden characters, line breaks that fake a section header, text that imitates the harness's own slots. Prior art offers no pack-for-agent equivalent (no source found); this is a first-principles point (INFERENCE).
5. **Trust boundary between author and consumer.** Renovate and VS Code both treat configuration that can redirect execution as needing explicit trust. Here the owner's value is trusted (the owner wrote it and commits it), the pack author's text is trusted only after approval, and a task field from a tracker is **untrusted** (R§1.4). That asymmetry is the main argument for or against one shared mechanism (R§4).
6. **Secrets.** Terraform and Helm show that "sensitive" markings are a display concern and do not stop values reaching state. Delivery has its own masking (`src/secrets.ts`, shape- and name-based, `SHORTEST = 8`), applying to reports and items. Whether a pack setting may be secret at all is a decision, not a fact (A8).

## 3. Interactions

### 3.1 Approval hashing

- Facts: values live outside the fingerprinted files (R§1.2), so **changing an owner's value does not invalidate approval**. Changing the pack's declaration (names, defaults, types, a new required setting) edits `pack.json` and **does** invalidate it until `update`/`approve`.
- What approval then covers: what the owner approved was the pack with its **declared defaults**. An owner override can change what the agent is told or the hold threshold; that is the owner's own act, comparable to `domain` text, not a pack change. But it means the approved account (Item 2) is not what runs when a value differs. Two readings: (a) approval covers the pack, values are the owner's responsibility and are visible in config diff in version control (the install design's stance: "version control is the audit trail", install design line 120); (b) include resolved prompts in what the owner sees. Inspection "values that would apply" (criterion 4) is the visible bridge.
- Widening: the `Change` direction logic treats a lowered hold as narrower and a lifted hold as wider (`compare.ts:28-37`). If hold is a setting, an update that changes the **default** needs a `Change` kind with direction, otherwise the four-part update report omits a widening (R§1.7).
- A new **required** setting added by an update would turn a previously `ok` pack into one that cannot run until the owner supplies a value. This is a second refusal on the run path beside the approval states (`refuseUnusable`); whether it belongs in the pack state machine or in config validation is open (A5).
- Determinism: pinning resolved text at run create (R§1.4) keeps a resumed run identical even if the config changes mid-run.

### 3.2 Item 6 (editor support)

- The packs' own JSON Schema exists (`packSchema`, R§1.1); a project-config schema does not (R§1.3). Item 6's third criterion needs the config schema to include per-pack settings, which come from pack **manifests** found by name (built-in `packs/`, folders listed in `packs`, `.delivery/packs/<name>/`).
- Design pressure: the shape of the owner's values key decides whether a static schema can describe it. A key per pack name with a fixed `object` value cannot be completed in an editor without pack-specific schema generation; a generated, project-specific schema (read the packs the project names, emit `properties` per pack setting) can. `delivery validate` and the editor must agree (Item 6 criterion 2), so the generator and `validate` should use the same zod source (consistent with the in-estate pattern, packs-for-any-workflow design line 281).
- "Same message in editor and `validate`" is easier if the pack setting declaration is itself expressible as a JSON Schema fragment (type, enum, default, description), since then one definition feeds loader validation, inspection and editor.

### 3.3 Item 9 (custom gates) and the roadmap's claim

- The roadmap claims a shared mechanism "removes the commonest reason for a custom gate". Evidence: the survey's custom gates existed to read `file`, `package` and `to` (R§1.5), which are **per-task fields**, not project-wide settings. Settings alone do not give a gate those values; only exposing task fields to command gates does. So the claim holds only if the mechanism covers task fields in gates, not if "settings" means per-project values.
- Second condition: a pack cannot carry a gate (D1 and `DATA_ONLY`, R§0, R§1.1). The project's gate is a project string. For a *pack* to benefit, either (i) the **project's** command gate could reference task fields, which helps projects but not "packs that carry custom gates" (Item 9's subject), or (ii) packs may carry a templated command, which D1 excludes and the roadmap's Item 1 constraint (data only) arguably contradicts: a command with a placeholder is still "commands" (`DATA_ONLY`). Whether (ii) is acceptable is a decision for the owner of the roadmap, not something a document already settles (A4).
- Also, custom gates are shared across concurrent tasks (survey item 6) but that is out of scope here.

### 3.4 Do settings and task fields share one mechanism? Facts only, for the designers

| Dimension | Task field `{{task.x}}` today | Pack setting (as roadmap describes) |
|---|---|---|
| Written by | Whoever writes the item: the scan agent, an owner, or a tracker user (R§1.4) | The owner, in project configuration |
| Trust | Untrusted for tracker items (`sources-run.ts:287-291`) | Trusted after commit |
| Scope | One item or run | The project, all runs |
| Known when | Run start (taskDef in header) | Config load (before pin) |
| Declared by pack? | No (free-form; unmatched left as written, a run does not warn) | Yes (required by criterion 1) |
| Validated before use? | No (`unmatchedPlaceholders` is warn-only in `preview`) | Yes by criterion 2 |
| Reaches gate? | No | Roadmap says "checks" (A3) |

Mechanical overlap: one placeholder syntax and one substitution function (`interpolateTask`, `prompt-assembly.ts:108`) could serve both, and section 6.7 item 3 says exactly this ("Item 4 can add `{{settings.<name>}}` to the same function"). Difference of kind: declaration, validation, trust. These are the facts; the decision is the architect's and product-designer's.

## 4. Ambiguities in the roadmap text

- **A1. "Not a second format change" (Item 4 Notes, line 169).** Already read by the Item 1 design as "additive within `/3`" (design line 240, which itself flags it). Under the `/3` additive definition (line 206), adding `settings` as an optional top-level key is additive; making a setting required for a pack that was approved without it is a runtime refusal, not a format change. Confirm the additive reading still holds for any new `kind`-level key (e.g. a setting referenced from `hold`).
- **A2. "The test command" as a setting.** Packs carry no gate (D1) and the project's gate already has its own configuration and inference (R§1.6). A pack "test command" can only mean: text for the agent's prompt, or a value the pack's *prompt* mentions. If it is meant to change what the harness runs to judge work, that conflicts with D1 and `DATA_ONLY`.
- **A3. "Values reach the pack's prompts and checks" (criterion 3).** In `/3`, a pack's checks are harness-owned item check kinds written by the scan agent (R§1.6), guards are a closed enum, and hold is a threshold. "Checks" could mean: the guards, the hold, the item `check` the scan writes (e.g. a `pattern-absent` path pattern from a file-layout setting), or a command gate (excluded). The criterion names no mechanism for any.
- **A4. "Command gates cannot see task fields ... visible to command gates" (Notes).** The finding concerns the **project's** command gate and per-task fields; Item 9 is about **packs** carrying gates. These are different beneficiaries. Also unclear: whether Item 4 itself is to change gate behaviour, or only to decide the principle (the Notes say "decides whether"; the Item 1 design says gate visibility is "engine behaviour, not format").
- **A5. "Unset required setting is refused with a message naming it."** Refused when? Config load (`validate`), `packs add`/`approve`, `inspect`, `review`, or only at run start? Refused for which commands (does `delivery packs` listing need values)? What for a pack the project names but never runs?
- **A6. "Supplies values in the project's configuration."** No existing place names an installed or built-in pack (R§1.3); `packs` holds paths. Whether values are per pack, per workflow (6.7 item 2 hints at scoping), or global to the project is unstated. `.js` configs cannot be read by inspection (R§1.3).
- **A7. "Settings" naming.** Collides with the code's meaning (whole configuration) and with VS Code's usage; owner-facing word may differ (e.g. "options"), and persona language in `docs/personas.md` is out of this brief's editing scope.
- **A8. Types and secrets.** Roadmap lists a command, a file layout and a severity, i.e. at least string, list and enum. Whether numbers, booleans, secrets, or values from environment variables are in scope is unstated. Secrets would conflict with a committed config and with prompts being shown by `preview`/inspection.
- **A9. "Defaults" for a required setting.** "With defaults" and "unset required" together imply two classes (with default, without). Whether a setting with a default can also be "required" (must be explicitly confirmed) is unstated; Terraform's rule (no default = required) is the simplest.
- **A10. "Shows the settings and the values that would apply" (criterion 4).** For a pack not named in config, for a `.js` config (inspection reads data only), and for an unset required setting, what is shown? Does "values" include the resolved prompt text, or only the table?
- **A11. Interaction with Item 5.** `packs check` runs a pack with no project config (R§1.8); how a pack with required settings is checked is unstated (Item 5 depends on Item 4).
- **A12. Existing packs.** `{{settings.` reservation is documented but unenforced (R§1.1). Whether to enforce it as a refusal now (a breaking change for a `/3` pack that uses it, though probably empty) is not decided.
- **A13. Update reporting.** Item 3 requires the owner "sees what changed when updating"; if settings are in the format, a changed default or new required setting is a change that matters, but `Change` has no such kind (R§1.7) and Item 3 is marked complete.
